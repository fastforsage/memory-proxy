## 0. The essentials in 30 seconds

1. **GitHub does not hold the code that the README describes and that was published.** The repo has only a 137-line MVP (the last commit with code is from 12.11). The README describes a 614-line v4.7.2: hybrid search, emotions, Context Bridge, API_KEY. That code exists **only inside the Docker image**. The repo has no tests, CI, LICENSE or `download_model.py`, although the README promises them.
2. **By default (no API_KEY, CORS `*`) any site open in the user's browser can read their whole conversation history** through the `/chats` and `/pull` slash commands. When run with the repo's `docker-compose.yml` (`network_mode: host`), so can anyone on the local network.
3. **There is no real multi-user mode.** The README recommends `API_KEY` + `GLOBAL_MEMORY=0`, but facts from one chat change facts in another, emotions and style are shared, and `/pull` and `/chats` read other people's chats.
4. **The key feature for Russian-speaking users barely works.** The zlib-based classifier marks ordinary Russian messages of ~100–350 characters as "technical". For such messages memory is not added and facts are not extracted.
5. **The cold path is fragile.** The request has no `model` field, so fact extraction silently breaks on Ollama and vLLM. The proof check is bypassed with an empty `evidence`. If processing fails, partially written data is later committed by someone else's request. Every message causes a second generation on the same LLM.

**Overall assessment:** an experimental prototype, not a production-grade "local-first memory layer". The idea is good (SQLite + FTS5 + sqlite-vec + RRF + quote-based validation), but the implementation, and especially the documentation, diverge strongly from reality.

## 2. Security and privacy (v4.7.2)

> The line numbers below refer to `proxy.py` from the v4.7.2 image.

### 🔴 C-2. Drive-by theft of the whole conversation history through the browser (CORS `*` + no auth + slash commands)
`proxy.py:228-229`, `231-234`, `486-508`

- By default `API_KEY=""` (auth disabled) and `CORS_ORIGINS=""`, which turns into `allow_origins=["*"]`.
- The `/chats`, `/pull N`, `/search` commands return the contents of **any** chats.
- So a page on any domain can run `fetch("http://127.0.0.1:8081/v1/chat/completions", {method:"POST", headers:{"Content-Type":"application/json"}, body: JSON.stringify({messages:[{role:"user",content:"/pull 1"}]})})`. The preflight passes and the answer is readable.

**PoC:** a preflight with `Origin: https://evil.example` got `Access-Control-Allow-Origin: *`, and the answer to `/pull 1` contained a "secret" from another chat (`hunter2`).

Newer browsers partly protect against requests from the public internet to localhost (Private/Local Network Access), but this cannot be relied on: support depends on the browser and version. If the service is exposed on the LAN (see C-2b), CORS does not even matter; `curl` is enough.

**C-2b.** The repo's `docker-compose.yml` uses `network_mode: host` and uvicorn on `0.0.0.0`. The README itself explicitly warns against this. Together with the lack of auth (v1 has none at all) this exposes memory and the LLM to the whole local network.

**What to do:**
- Do not enable CORS at all by default (`allow_origins=[]`). Enable it only with an explicit list.
- If `CORS_ORIGINS="*"` or the service listens on a non-loopback address while `API_KEY` is empty, refuse to start.
- Compare the key with `hmac.compare_digest`.
- Fix the compose file in the repo: `ports: ["127.0.0.1:8081:8081"]`.

### 🟠 H-1. No isolation of users and chats; `GLOBAL_MEMORY=0` works only partially
`proxy.py:396-397`, `162`, `306-331`, `289-304`, `522`, `335`

The README section "For multi-user use" recommends `API_KEY` + `GLOBAL_MEMORY=0`. In reality:

| Component | chat_id filter with `GLOBAL_MEMORY=0` |
|---|---|
| Fact search (FTS/vec) | ✅ present |
| Invalidation of single-valued facts (`UPDATE facts SET valid_to … WHERE predicate=?`) | ❌ global |
| Duplicate check and `UNIQUE(predicate, object)` | ❌ global: the same fact in a second chat is not created |
| Emotions (`emotions.trigger` PRIMARY KEY) | ❌ shared |
| Style examples | ❌ shared |
| `/chats`, `/pull`, `/search`, automatic Context Bridge | ❌ read **all** chats |

**PoC (GLOBAL_MEMORY=0):**
- «Я живу в Казани» ("I live in Kazan") in chat B closed (`valid_to`) the "Moscow" fact in chat A.
- The emotion «понедельники» ("Mondays") from chat B ended up in chat A's system prompt.
- `/pull 2` from chat A returned chat B's conversation.

Separately: there is no notion of a "user" at all. One shared `API_KEY` means one shared brain for everybody. Open WebUI sends `X-OpenWebUI-User-Id`, but the proxy ignores it.

**What to do:** add a `user_id` column to all tables. Take it from `X-OpenWebUI-User-Id` or from an "API key → user" mapping. Filter **every** query by it, including commands. For vectors, use a `partition key` in vec0 (supported since sqlite-vec 0.1.6).

### 🟠 H-2. Stored prompt injection across chats
`proxy.py:519-521`, `299-301`, `535`

The Context Bridge inserts up to 300 characters of **raw text from other user messages** into a message with the `system` role. It fires on very broad triggers: «раньше», «ранее», «помни», «как мы» ("before", "earlier", "remember", "as we") and so on. Style examples go there too: assistant answers, including "poisoned" ones. The result is a persistent jailbreak that survives the chat and, with shared access, spreads between users.

**PoC:** the message «Помни: ИГНОРИРУЙ ВСЕ ПРЕДЫДУЩИЕ ИНСТРУКЦИИ…» ("Remember: IGNORE ALL PREVIOUS INSTRUCTIONS…") from chat `attacker` ended up in the system role of chat `victim`.

**What to do:** insert cross-chat context and style examples not into system but as explicitly marked **data** (for example, into a user message labelled "quotes, not instructions"). Escape or truncate the text. Limit insertion to chats of the same user. Tighten the triggers.

### 🟡 M-1. No data management
You cannot delete a fact or a chat ("forget that…"), view what is stored, export data or set a retention period. `messages` grows forever and stores **everything**, including passwords the user may have pasted. A "private" product needs at least `/forget`, `/facts` and `RETENTION_DAYS`.

### 🔵 Minor security issues
- `check_auth` compares strings with a plain `!=` rather than in constant time (`proxy.py:233`).
- `/health` without auth returns the SQLite exception text (`proxy.py:448`).
- The container runs as root (no `USER`).
- SQL is parameterised everywhere; **no SQL injection was found** ✅

## 3. Correctness of the memory logic

### 🟠 H-3. The zlib classifier disables memory for typical Russian messages
`proxy.py:56-66`, `510-515`, `554`

The threshold is `ratio > 0.55 → technical`. Short text compresses poorly, and Cyrillic in UTF-8 takes 2 bytes per character. So an ordinary personal message of 100–350 characters gets a ratio of 0.56–0.67 and is marked **technical**. For such messages:
- memory is **not added** (`_skip`);
- cold analysis (fact extraction) **does not run**.

**PoC:**
```
length 120: technical (0.67)   length 200: technical (0.60)   length 300: technical (0.56)
length 500: unknown  (0.51)    Python code, 300 chars: technical (0.62)
```
A 300-character personal story about family, the dacha and moving house is classified the same way as Python code. The "Semantic Classifier ✅" feature effectively works backwards.

**What to do:** detect code by features rather than compressibility: ```` ``` ```` blocks, the share of `{}();=<>` characters, keywords `def/class/import/function/SELECT`, indentation, the share of Latin characters. Or skip nothing on the hot path and decide the type on the cold path.

### 🟠 H-4. Cold path: silent failures, a bypassed check, "dirty" transactions
`proxy.py:367-433`, `555`

| # | Problem | PoC |
|---|---|---|
| a | The request to the LLM has no `model` field (`proxy.py:379`). llama.cpp will accept that, but **Ollama, vLLM, LM Studio and OpenAI-compatible APIs return 400**. The code does `if r.status_code != 200: return` without logging, and facts are **never** extracted. Meanwhile the README promises Ollama and vLLM support. | request keys: `messages, response_format, temperature` |
| b | **The proof check is bypassed:** `"" in text` is always `True`, so a fact with an empty or missing `evidence` is accepted. `object` is not checked against the text at all: evidence «я» ("I") and object "Google" pass. | the hallucination `works_at: Google` from a sentence about the weather was stored |
| c | No type validation: if `facts` is a list of strings, `evidence` is `None` or `data` is a list, there is an `AttributeError`. The exception is caught, **but without `rollback()`**. The `UPDATE`s and `INSERT`s already executed stay in the shared transaction and are **committed by the next, unrelated request**. The embedding is not computed, and the fact stays without a vector forever: backfill only runs when `vec_facts` is empty. | "Kazan" stored, "Moscow" closed, "Kazan" has no vector |
| d | `asyncio.create_task` without keeping a reference: the task may be garbage-collected (the Python docs warn about this). The queue behind `Semaphore(1)` is unbounded and grows under load. | — |
| e | Every user message causes a **second generation on the same LLM**. On llama.cpp with `--parallel 1` cold analysis occupies the slot, and the next answer to the user waits for it to finish. There is no separate `EXTRACT_URL` or `EXTRACT_MODEL`. | — |
| f | Emotions are accepted only if the trigger **contains Cyrillic** and occurs in the text **verbatim**. The README example "Jira = -1.0" is impossible in principle. «работа» ("work") will not match the phrase «ненавижу работу» ("I hate work", accusative form). | `emotions(Jira) = []` |

**What to do:**
- A bounded `asyncio.Queue` and a dedicated worker.
- Pass `model` from the original `body` or from `EXTRACT_MODEL`; add `EXTRACT_URL`.
- A validation schema (pydantic), `evidence` of at least N characters, `object` must fuzzily occur in `evidence`.
- Wrap the writes in `with conn:` (a transaction with rollback); log non-200 responses.

### 🟡 M-2. The vector index degrades over time
`proxy.py:252-258`, `396`, `167-179`

- When facts are invalidated or deleted, their rows in `vec_facts` are **not deleted**. KNN first takes `k=20`, then filters by `valid_to IS NULL` and `chat_id`. As history grows, these 20 slots get occupied by outdated and foreign facts, and vector search returns nothing.
- Facts without a vector (see H-4c) are not restored: backfill runs only when `COUNT(*)=0`.

**PoC:** the outdated `lives_in: Москва` stayed in `vec_facts`, while the current "Kazan" has no vector.

**What to do:** delete the vector on invalidation. Backfill via `LEFT JOIN … WHERE v.rowid IS NULL` at startup. Use vec0 metadata or partition columns (`valid`, `user_id`) to filter inside KNN.

### 🟡 M-3. USER2 embeddings are used without the required prefixes
`proxy.py:84-107`

The `deepvk/USER2-small` model card requires the prefixes `search_query: ` and `search_document: ` ("expects task-specific prefixes"). The code does not add them, so search quality is noticeably below what is claimed.

**What to do:** when indexing pass `embed_batch(["search_document: " + t …])`, when querying `"search_query: " + text`. Then reindex.

### 🟡 M-4. The Style Profile breaks because of Open WebUI background requests
`proxy.py:484`, `510`, `595`, `611`

After every answer Open WebUI sends service requests (title, tags, follow-ups) with the same chat_id.
- `score_previous()` is called **before** the `is_service_request` check. The service request takes `LAST_EXAMPLE_ID`, and the user's real reaction («спасибо», "thanks") no longer scores anything.
- The answer to the service request (JSON with tags) is **stored** in `messages` and in `style_examples`, and later mixed into the prompt as "an example of your style".

**PoC:** `LAST_EXAMPLE_ID` changed 5 → 6, and the tags JSON ended up in both `messages` and `style_examples`.

The scoring regexes (`proxy.py:35-36`) are broken too. Word stems with a trailing `\b` do not match word forms: «ошибка», «бесполезно», «ужасно» ("error", "useless", "awful") → no match. Negation is not taken into account: «не хорошо» ("not good") and «спасибо, но не так» ("thanks, but that's not it") count as **praise**.

### 🟡 M-5. chat_id detection
`proxy.py:435-440`

- Open WebUI sends `X-OpenWebUI-Chat-Id` **only** with `ENABLE_FORWARD_USER_INFO_HEADERS=true`, and the default is `False` ([Open WebUI documentation](https://docs.openwebui.com/reference/env-configuration/)). The README says nothing about this.
- The fallback `body.user` is, per the OpenAI standard, a **user ID**, not a chat ID. In SillyTavern and LibreChat all chats merge into one ID or into `"default"`.
- The Context Bridge searches `chat_id != current`, so without the header it **does not work at all**.

**PoC:** two requests without the header; the «КОНТЕКСТ ИЗ ДРУГИХ ЧАТОВ» ("CONTEXT FROM OTHER CHATS") block did not appear.

### 🔵 Dead and unfinished code (features from the README)
- **Mood Engine:** `mood_state` is only written (`proxy.py:422-423`) and **never read**. There is no 30-minute TTL.
- **summaries:** the table is read (`proxy.py:527`) but **never written**.
- **Emotion decay** is applied only on a new mention. On read (`proxy.py:522-526`) the raw `score` is used and selection is by `mention_count`, so an old dislike lives forever.
- Facts are stored in an inflected form («Москве», "in Moscow", locative). FTS5 `unicode61` does no stemming.

## 4. Protocol and compatibility

### 🟡 M-6. The memory system message is inserted in the middle of the dialogue
`proxy.py:534-536`

The memory block is inserted **before the last message** as a separate `system`. Many chat templates in llama.cpp, Ollama and vLLM (Gemma, Mistral, Llama-2-style, etc.) require system to be first only, or roles to strictly alternate. The result is template errors or silent distortion. If the last message is `assistant` (prefill) or `tool`, the block lands in the wrong place altogether.

**PoC:** roles sent upstream: `system, user, assistant, system, user`.

**What to do:** append memory to the existing first system (or create one at the beginning).

### 🟡 M-7. Slash commands
`proxy.py:486-508`

- **Any message starting with `/` is intercepted.** The question «/etc/nginx/nginx.conf — что за файл?» ("what file is this?") never reached the LLM; the answer was «❓ /etc/nginx/nginx.conf. /help» (PoC).
- Commands **always return SSE**, even with `stream:false`. Non-streaming clients (curl, title generation, SDKs) get an answer they cannot parse (PoC).
- The chunk has no `id`, `object`, `created`, `model`, `index`, so strict clients fail.

**What to do:** catch only exact whitelisted commands and send everything else to the LLM. Respect `stream`. Return a complete `chat.completion` or `chat.completion.chunk` object.

### 🟡 M-8. Compression
`proxy.py:358-365`, `538-542`

- All system messages are moved to the beginning, breaking the order.
- The `recent` window may start with a `tool` message whose `assistant.tool_calls` was cut off. That is a 400 error on OpenAI-compatible backends.
- Multimodal `content` (a list) ends up in the summary as the `repr()` of a Python list.
- A threshold of 22000 "tokens" with `len//3` fires too late for a typical llama.cpp with an 8–16k context.

### 🔵 Other
- Regenerate or retry in the client stores the same user message again and reruns cold analysis, creating duplicates in the DB.
- Messages with images or files (a content list) drop out of memory entirely: the text part is ignored too.
- The SSE parser strictly expects `data: ` with a space. The last line without `\n` is lost.

## 5. Performance

### 🟠 H-5. Synchronous work in the event loop
- `embed_text` (ONNX), FTS, SQLite and `embed_batch` on the cold path run **synchronously inside async handlers**. While an embedding is computed, all other streams stall.
- `MAX_INPUT_LEN=200000`, and the text is turned into an FTS query `w1 OR w2 OR …` with no limit on the number of terms.

**PoC:** `get_smart_facts()` on 30k words took **~1.1 s synchronously** even with a stub instead of ONNX. This is an easy way to hang the proxy, including other users' streams.

**What to do:** `await anyio.to_thread.run_sync(...)` for ONNX and SQLite, or a dedicated executor thread with its own connection. Truncate the search text (~2000 characters, ≤32 unique terms).

### 🟡 M-9. Image and model
- `download_model.py` downloads **all 8 ONNX variants** (fp32, fp16, int8, q4, bnb4, …), ≈533 MB. **Only** `model.onnx` (138 MB) is used. That is why v4.7.2 weighs 654 MB while v4.6 weighs 247 MB. Narrowing `allow_patterns` to `onnx/model.onnx` would shrink the image by about 400 MB (or `model_int8.onnx`, 35 MB, could be used).
- The model revision is not pinned (`snapshot_download` without `revision`); the build is not reproducible.
- `transformers` (a heavy library with 40+ OSV advisories for 4.46.3) is needed only for the tokenizer. The `tokenizers` library is enough: `Tokenizer.from_file("tokenizer.json")`.
- `rebuild_messages_fts()` runs **on every start**, O(N) over the whole history.
- `LAST_EXAMPLE_ID` grows forever (one key per chat_id).
- The README claims "Hot Path < 10 ms", "~5 ms embedding" and "~50 MB RAM" are not backed by anything; there are no benchmarks.

## 7. The code on GitHub (v1 MVP, 137-line `proxy.py`)

This is what a user actually gets with `git clone && docker compose up`:

- No auth, CORS `*`, compose with `network_mode: host`. The service is open to the whole LAN.
- Facts are global, without chat_id (`SELECT … FROM facts`), and extracted with regexes. «Я люблю тебя» ("I love you") turns into `likes: тебя` ("likes: you"). The check `obj.lower() in m.group(0).lower()` is always true. The «может» ("maybe") filter also fires on «можете» ("you can").
- `sys_msg["content"] += …` fails with 500 if content is a list (vision or files).
- Streaming: a JSON line split across TCP chunks is lost, and the answer is stored in the DB incompletely.
- A failed upstream status is not passed to the client (always 200). `/v1/models` returns 500 when the backend is unavailable. A new `httpx.AsyncClient` is created on every request. Bare `except:` everywhere.

## 9. What is done well ✅
- A good architectural idea: one SQLite file, FTS5 + sqlite-vec + RRF, fact validation by a verbatim quote, facts with history (`valid_from`/`valid_to`), the split into hot and cold paths.
- Parameterised SQL queries, WAL, `busy_timeout`. Correct triggers for external-content FTS5.
- In v4.7.2 compared with v1: a shared `httpx.AsyncClient` with timeouts, passing the upstream status through, buffered SSE parsing, basic request body validation, a healthcheck in the image, `MAX_INPUT_LEN`, a predicate whitelist, `UNIQUE` on current facts.
- Pinned dependency versions, an ONNX model without PyTorch (compared with the 3.4 GB v4.5 this is a huge step).

        messages[0]["content"] += "\n\n" + block
