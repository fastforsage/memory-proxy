## 0. Главное за 30 секунд

1. **В GitHub лежит не тот код, который описан в README и опубликован.** В репозитории есть только MVP на 137 строк (последний коммит с кодом — 12.11). README описывает v4.7.2 на 614 строк: гибридный поиск, эмоции, Context Bridge, API_KEY. Этот код есть **только внутри Docker-образа**. В репозитории нет тестов, CI, LICENSE, `download_model.py`, хотя README их обещает.
2. **По умолчанию (без API_KEY, CORS `*`) любой сайт, открытый в браузере пользователя, может прочитать всю его переписку** через слэш-команды `/chats` и `/pull`. Если запускать по `docker-compose.yml` из репозитория (`network_mode: host`), то ещё и любой в локальной сети.
3. **Многопользовательского режима на самом деле нет.** README советует `API_KEY` + `GLOBAL_MEMORY=0`, но факты одного чата меняют факты другого, эмоции и стиль общие, а `/pull` и `/chats` читают чужие чаты.
4. **Ключевая фича для русскоязычных пользователей почти не работает.** Классификатор на zlib помечает обычные русские сообщения длиной ~100–350 символов как «technical». Для таких сообщений память не подставляется, факты не извлекаются.
5. **Cold path хрупкий.** В запросе нет поля `model`, поэтому на Ollama и vLLM извлечение фактов тихо ломается. Proof-check обходится пустым `evidence`. Если обработка падает, частично записанные данные потом коммитит чужой запрос. Каждое сообщение даёт вторую генерацию на том же LLM.

**Итоговая оценка:** экспериментальный прототип, а не «local-first memory layer» уровня продакшена. Идея хорошая (SQLite + FTS5 + sqlite-vec + RRF + проверка цитатой), реализация и особенно документация сильно расходятся с действительностью.

## 2. Безопасность и приватность (v4.7.2)

> Номера строк ниже относятся к `proxy.py` из образа v4.7.2.

### 🔴 C-2. Drive-by кража всей переписки через браузер (CORS `*` + нет auth + слэш-команды)
`proxy.py:228-229`, `231-234`, `486-508`

- По умолчанию `API_KEY=""` (auth отключена) и `CORS_ORIGINS=""`, что превращается в `allow_origins=["*"]`.
- Команды `/chats`, `/pull N`, `/search` возвращают содержимое **любых** чатов.
- Значит, страница на любом домене может выполнить `fetch("http://127.0.0.1:8081/v1/chat/completions", {method:"POST", headers:{"Content-Type":"application/json"}, body: JSON.stringify({messages:[{role:"user",content:"/pull 1"}]})})`. Preflight проходит, ответ читается.

**PoC:** preflight с `Origin: https://evil.example` получил `Access-Control-Allow-Origin: *`, а ответ на `/pull 1` содержал «секрет» из другого чата (`hunter2`).

Новые браузеры частично защищают от запросов из публичной сети к localhost (Private/Local Network Access), но полагаться на это нельзя: поддержка зависит от браузера и версии. Если сервис открыт в LAN (см. C-2b), CORS вообще не нужен — достаточно `curl`.

**C-2b.** `docker-compose.yml` в репозитории использует `network_mode: host` и uvicorn на `0.0.0.0`. Против этого же README прямо предупреждает. Вместе с отсутствием auth (в v1 её нет совсем) это открывает память и LLM всей локальной сети.

**Что сделать:**
- По умолчанию вообще не включать CORS (`allow_origins=[]`). Включать только явным списком.
- Если `CORS_ORIGINS="*"` или сервис слушает не loopback, а `API_KEY` пуст, отказываться стартовать.
- Сравнивать ключ через `hmac.compare_digest`.
- Исправить compose в репозитории: `ports: ["127.0.0.1:8081:8081"]`.

### 🟠 H-1. Изоляции пользователей и чатов нет, `GLOBAL_MEMORY=0` работает лишь частично
`proxy.py:396-397`, `162`, `306-331`, `289-304`, `522`, `335`

README в разделе «Для многопользовательского использования» советует `API_KEY` + `GLOBAL_MEMORY=0`. На деле:

| Компонент | Фильтр по chat_id при `GLOBAL_MEMORY=0` |
|---|---|
| Поиск фактов (FTS/vec) | ✅ есть |
| Инвалидация single-valued фактов (`UPDATE facts SET valid_to … WHERE predicate=?`) | ❌ глобальная |
| Проверка дубликата и `UNIQUE(predicate, object)` | ❌ глобальные: одинаковый факт во втором чате не создаётся |
| Эмоции (`emotions.trigger` PRIMARY KEY) | ❌ общие |
| Style examples | ❌ общие |
| `/chats`, `/pull`, `/search`, авто-Context Bridge | ❌ читают **все** чаты |

**PoC (GLOBAL_MEMORY=0):**
- «Я живу в Казани» в чате B закрыл (`valid_to`) факт «Москва» в чате A.
- Эмоция «понедельники» из чата B попала в system-промпт чата A.
- `/pull 2` из чата A вернул переписку чата B.

Отдельно: понятия «пользователь» нет вообще. Один общий `API_KEY` — это один общий мозг для всех. Open WebUI присылает `X-OpenWebUI-User-Id`, но прокси его игнорирует.

**Что сделать:** добавить колонку `user_id` во все таблицы. Брать его из `X-OpenWebUI-User-Id` или из сопоставления «API-ключ → пользователь». Фильтровать по нему **каждый** запрос, включая команды. Для векторов использовать `partition key` в vec0 (поддерживается с sqlite-vec 0.1.6).

### 🟠 H-2. Хранимая prompt-инъекция между чатами
`proxy.py:519-521`, `299-301`, `535`

Context Bridge вставляет до 300 символов **сырого текста других пользовательских сообщений** в сообщение с ролью `system`. Срабатывает по очень широким триггерам: «раньше», «ранее», «помни», «как мы» и т. п. Туда же попадают style examples: ответы ассистента, включая «отравленные». Получается постоянный jailbreak, который переживает чат и, при общем доступе, переходит между пользователями.

**PoC:** сообщение «Помни: ИГНОРИРУЙ ВСЕ ПРЕДЫДУЩИЕ ИНСТРУКЦИИ…» из чата `attacker` попало в system-роль чата `victim`.

**Что сделать:** подставлять кросс-чат контекст и примеры стиля не в system, а как явно помеченные **данные** (например, в user-сообщение с пометкой «цитаты, не инструкции»). Экранировать или обрезать текст. Ограничить подстановку чатами того же пользователя. Ужесточить триггеры.

### 🟡 M-1. Нет управления данными
Нельзя удалить факт или чат («забудь, что…»), посмотреть сохранённое, экспортировать данные, задать срок хранения. `messages` растёт бесконечно и хранит **всё**, включая пароли, которые пользователь мог вставить. Для «приватного» продукта нужны хотя бы `/forget`, `/facts` и `RETENTION_DAYS`.

## 3. Корректность логики памяти

### 🟠 H-3. Классификатор на zlib отключает память для типичных русских сообщений
`proxy.py:56-66`, `510-515`, `554`

Порог `ratio > 0.55 → technical`. Короткий текст плохо сжимается, а кириллица в UTF-8 занимает 2 байта на символ. Поэтому обычная личная реплика на 100–350 символов получает ratio 0.56–0.67 и помечается **technical**. Для таких сообщений:
- память **не подставляется** (`_skip`);
- cold-анализ (извлечение фактов) **не запускается**.

**PoC:**
```
длина 120: technical (0.67)   длина 200: technical (0.60)   длина 300: technical (0.56)
длина 500: unknown  (0.51)    Python-код 300 симв.: technical (0.62)
```
Личный рассказ о семье, даче и переезде на 300 символов классифицируется так же, как Python-код. Фича «Semantic Classifier ✅» по сути работает наоборот.

**Что сделать:** определять код признаками, а не степенью сжатия: блоки ```` ``` ````, доля символов `{}();=<>`, ключевые слова `def/class/import/function/SELECT`, отступы, доля латиницы. Либо ничего не пропускать в hot path, а тип решать в cold path.

### 🟠 H-4. Cold path: тихие отказы, обход проверки, «грязные» транзакции
`proxy.py:367-433`, `555`

| # | Проблема | PoC |
|---|---|---|
| a | В запросе к LLM нет поля `model` (`proxy.py:379`). llama.cpp это проглотит, а **Ollama, vLLM, LM Studio и OpenAI-совместимые API вернут 400**. Код делает `if r.status_code != 200: return` без лога, и факты **никогда** не извлекаются. README при этом обещает поддержку Ollama и vLLM. | ключи запроса: `messages, response_format, temperature` |
| b | **Proof-check обходится:** `"" in text` всегда `True`, поэтому факт с пустым или отсутствующим `evidence` принимается. `object` вообще не сверяется с текстом: evidence «я» и object «Google» пройдут. | галлюцинация `works_at: Google` из фразы про погоду сохранена |
| c | Нет валидации типов: если `facts` — список строк, `evidence` равно `None` или `data` — список, будет `AttributeError`. Исключение ловится, **но без `rollback()`**. Уже выполненные `UPDATE` и `INSERT` остаются в общей транзакции и **коммитятся следующим чужим запросом**. Embedding не выполняется, и факт навсегда остаётся без вектора: backfill работает только при пустой `vec_facts`. | «Казань» сохранена, «Москва» закрыта, вектора у «Казани» нет |
| d | `asyncio.create_task` без сохранения ссылки: задачу может собрать GC (это предупреждение есть в документации Python). Очередь за `Semaphore(1)` не ограничена и растёт под нагрузкой. | — |
| e | Каждое пользовательское сообщение даёт **вторую генерацию на том же LLM**. На llama.cpp с `--parallel 1` cold-анализ занимает слот, и следующий ответ пользователю ждёт его окончания. Отдельного `EXTRACT_URL` или `EXTRACT_MODEL` нет. | — |
| f | Эмоции принимаются, только если триггер **содержит кириллицу** и встречается в тексте **дословно**. Пример из README «Jira = -1.0» невозможен в принципе. «работа» не пройдёт для фразы «ненавижу работу». | `emotions(Jira) = []` |

**Что сделать:**
- Ограниченная `asyncio.Queue` и отдельный воркер.
- Передавать `model` из исходного `body` или из `EXTRACT_MODEL`; добавить `EXTRACT_URL`.
- Схема валидации (pydantic), `evidence` длиной не меньше N символов, `object` должен нечётко встречаться в `evidence`.
- Обернуть запись в `with conn:` (транзакция с rollback); логировать не-200.

### 🟡 M-2. Векторный индекс деградирует со временем
`proxy.py:252-258`, `396`, `167-179`

- При инвалидации и удалении фактов строки в `vec_facts` **не удаляются**. KNN сначала берёт `k=20`, потом фильтрует `valid_to IS NULL` и `chat_id`. По мере роста истории эти 20 мест занимают устаревшие и чужие факты, и векторный поиск возвращает пусто.
- Факты без вектора (см. H-4c) не восстанавливаются: backfill идёт только при `COUNT(*)=0`.

**PoC:** устаревший `lives_in: Москва` остался в `vec_facts`, у актуального `Казань` вектора нет.

**Что сделать:** удалять вектор при инвалидации. Backfill через `LEFT JOIN … WHERE v.rowid IS NULL` при старте. Использовать metadata или partition-колонки vec0 (`valid`, `user_id`), чтобы фильтровать внутри KNN.

### 🟡 M-3. Эмбеддинги USER2 используются без обязательных префиксов
`proxy.py:84-107`

Карточка модели `deepvk/USER2-small` требует префиксов `search_query: ` и `search_document: ` («expects task-specific prefixes»). Код их не добавляет, поэтому качество поиска заметно ниже заявленного.

**Что сделать:** при индексации передавать `embed_batch(["search_document: " + t …])`, при запросе — `"search_query: " + text`. Затем переиндексировать.

### 🟡 M-4. Style Profile ломается из-за фоновых запросов Open WebUI
`proxy.py:484`, `510`, `595`, `611`

После каждого ответа Open WebUI шлёт служебные запросы (title, tags, follow-ups) с тем же chat_id.
- `score_previous()` вызывается **до** проверки `is_service_request`. Служебный запрос забирает `LAST_EXAMPLE_ID`, и настоящая реакция пользователя («спасибо») уже ничего не оценивает.
- Ответ служебного запроса (JSON с тегами) **сохраняется** в `messages` и в `style_examples`, а потом подмешивается в промпт как «пример твоего стиля».

**PoC:** `LAST_EXAMPLE_ID` сменился 5 → 6, JSON тегов оказался и в `messages`, и в `style_examples`.

Регулярки оценки (`proxy.py:35-36`) тоже сломаны. Основы слов с `\b` на конце не матчат словоформы: «ошибка», «бесполезно», «ужасно» → нет совпадения. Отрицание не учитывается: «не хорошо» и «спасибо, но не так» считаются **похвалой**.

### 🟡 M-5. Определение chat_id
`proxy.py:435-440`

- `X-OpenWebUI-Chat-Id` Open WebUI отправляет **только** при `ENABLE_FORWARD_USER_INFO_HEADERS=true`, а по умолчанию это `False` ([документация Open WebUI](https://docs.openwebui.com/reference/env-configuration/)). В README об этом ни слова.
- Запасной вариант `body.user` по стандарту OpenAI — это **ID пользователя**, а не чата. В SillyTavern и LibreChat все чаты сливаются в один ID или в `"default"`.
- Context Bridge ищет `chat_id != current`, поэтому без заголовка он **не работает вообще**.

**PoC:** два запроса без заголовка, блок «КОНТЕКСТ ИЗ ДРУГИХ ЧАТОВ» не появился.

### 🔵 Мёртвый и недоделанный код (функции из README)
- **Mood Engine:** `mood_state` только пишется (`proxy.py:422-423`), но **нигде не читается**. TTL 30 минут нет.
- **summaries:** таблица читается (`proxy.py:527`), но **нигде не пишется**.
- **Затухание эмоций** применяется только при новом упоминании. При чтении (`proxy.py:522-526`) берётся сырой `score`, выборка идёт по `mention_count`, так что старая неприязнь живёт вечно.
- Факты хранятся в падежной форме («Москве»). FTS5 `unicode61` не делает стемминг.

## 4. Протокол и совместимость

### 🟡 M-6. system-сообщение памяти вставляется посреди диалога
`proxy.py:534-536`

Блок памяти вставляется **перед последним сообщением** отдельным `system`. Многие chat-шаблоны в llama.cpp, Ollama и vLLM (Gemma, Mistral, Llama-2-style и др.) требуют, чтобы system был только первым, или чтобы роли строго чередовались. Отсюда ошибки шаблона или молчаливые искажения. Если последнее сообщение — `assistant` (prefill) или `tool`, блок вообще попадёт не туда.

**PoC:** роли в upstream: `system, user, assistant, system, user`.

**Что сделать:** дописывать память в существующий первый system (или создавать его в начале).

### 🟡 M-7. Слэш-команды
`proxy.py:486-508`

- **Перехватывается любое сообщение, начинающееся с `/`.** Вопрос «/etc/nginx/nginx.conf — что за файл?» не дошёл до LLM, ответ: «❓ /etc/nginx/nginx.conf. /help» (PoC).
- Команды **всегда возвращают SSE**, даже при `stream:false`. Клиенты без стриминга (curl, генерация заголовков, SDK) получают ответ, который не могут разобрать (PoC).
- В чанке нет `id`, `object`, `created`, `model`, `index`, поэтому строгие клиенты падают.

**Что сделать:** ловить только точные команды из белого списка, всё остальное отправлять в LLM. Уважать `stream`. Отдавать полноценный объект `chat.completion` или `chat.completion.chunk`.

### 🟡 M-8. Компрессия
`proxy.py:358-365`, `538-542`

- Все system-сообщения переносятся в начало, порядок нарушается.
- Окно `recent` может начаться с `tool`-сообщения, у которого отрезан `assistant.tool_calls`. Это ошибка 400 у OpenAI-совместимых бэкендов.
- Мультимодальный `content` (список) попадает в сводку как `repr()` питоновского списка.
- Порог 22000 «токенов» при `len//3` для типичного llama.cpp с контекстом 8–16k срабатывает слишком поздно.

### 🔵 Прочее
- Regenerate или retry в клиенте заново сохраняет то же user-сообщение и заново запускает cold-анализ, в БД появляются дубли.
- Сообщения с картинками или файлами (content-список) полностью выпадают из памяти: текстовая часть тоже игнорируется.
- Разбор SSE ожидает строго `data: ` с пробелом. Последняя строка без `\n` теряется.

## 5. Производительность

### 🟠 H-5. Синхронная работа в event loop
- `embed_text` (ONNX), FTS, SQLite и `embed_batch` в cold path выполняются **синхронно внутри async-обработчиков**. Пока считается эмбеддинг, все остальные стримы стоят.
- `MAX_INPUT_LEN=200000`, а из текста строится FTS-запрос `w1 OR w2 OR …` без ограничения числа термов.

**PoC:** `get_smart_facts()` на 30 тыс. слов занял **~1,1 с синхронно** даже с заглушкой вместо ONNX. Это простой способ «подвесить» прокси, в том числе для чужих стримов.

**Что сделать:** `await anyio.to_thread.run_sync(...)` для ONNX и SQLite, или отдельный поток-исполнитель со своим соединением. Обрезать текст для поиска (~2000 символов, ≤32 уникальных терма).

### 🟡 M-9. Образ и модель
- `download_model.py` скачивает **все 8 ONNX-вариантов** (fp32, fp16, int8, q4, bnb4, …), это ≈533 MB. Используется **только** `model.onnx` (138 MB). Поэтому v4.7.2 весит 654 MB, а v4.6 — 247 MB. Если сузить `allow_patterns` до `onnx/model.onnx`, образ похудеет примерно на 400 MB (или можно взять `model_int8.onnx`, 35 MB).
- Ревизия модели не зафиксирована (`snapshot_download` без `revision`), сборка не воспроизводима.
- `transformers` (тяжёлая библиотека, 40+ advisories в OSV для 4.46.3) нужна только ради токенизатора. Хватит библиотеки `tokenizers`: `Tokenizer.from_file("tokenizer.json")`.
- `rebuild_messages_fts()` выполняется **при каждом старте**, это O(N) по всей истории.
- `LAST_EXAMPLE_ID` растёт бесконечно (по ключу на каждый chat_id).
- Заявления README «Hot Path < 10 мс», «~5 мс embedding» и «~50 MB RAM» ничем не подтверждены, бенчмарков нет.

## 7. Код в GitHub (v1-MVP, `proxy.py` 137 строк)

Это то, что пользователь реально получит при `git clone && docker compose up`:

- Нет auth, CORS `*`, compose с `network_mode: host`. Сервис открыт всей LAN.
- Факты глобальные, без chat_id (`SELECT … FROM facts`), извлекаются regex-ами. «Я люблю тебя» превращается в `likes: тебя`. Проверка `obj.lower() in m.group(0).lower()` всегда истинна. Фильтр «может» срабатывает и на «можете».
- `sys_msg["content"] += …` падает с 500, если content — список (vision или файлы).
- Стриминг: JSON-строка, разорванная между TCP-чанками, теряется, и ответ в БД сохраняется не полностью.
- Неуспешный статус upstream не передаётся клиенту (всегда 200). `/v1/models` при недоступном бэкенде отвечает 500. На каждый запрос создаётся новый `httpx.AsyncClient`. Везде голые `except:`.
