# Модель эмбеддингов: USER2-small против granite-embedding-97m-multilingual-r2

**Русский** | [English](../en/design/embedding-model.md)

Статус: **исследование, 27.11.2026.** Код прокси не менялся. Скрипты и сырые результаты — [`../bench/embeddings/`](../bench/embeddings/README.md).

**Гипотеза (FR «мультиязычный семантический поиск»):** для архитектуры memory-proxy идеальной мультиязычной заменой штатной модели `onnx-community/USER2-small-ONNX` является `onnx-community/granite-embedding-97m-multilingual-r2-ONNX`.

## 0. Коротко

**Гипотеза не подтверждается.** granite заметно лучше на украинском, казахском, немецком, турецком и других языках, но на **русском — основном языке прокси — статистически значимо хуже**, медленнее на горячем пути, втрое тяжелее по памяти и без правок кода работает хуже USER2 на всех основных языках. Как **опция для пользователей, которые пишут не только по-русски и по-английски**, — хороший кандидат. Как замена по умолчанию — нет.

| Критерий «идеальной замены» | Результат | |
|---|---|---|
| Русский не хуже | доменный набор, русские запросы: MRR@10 **−0.161** [−0.264; −0.058]; Tatoeba rus→eng 0.815 против 0.938; RuBQ — паритет (−0.008, незначимо) | ❌ |
| Другие языки лучше | uk +0.230, de/kk/tr/es +0.414 (значимо); Wikipedia bg +0.050, de +0.135; Tatoeba de/fr/es/zh 0.88–0.95 против 0.02–0.22 | ✅ |
| Английский не хуже | доменный набор +0.003 (незначимо) | ✅ |
| Задержка горячего пути не растёт | эмбеддинг вопроса 300 симв.: 19.6 → 31.5 мс (×1.6); 2000 симв.: 159 → 292 мс | ❌ |
| Ресурсы домашнего сервера | ONNX 138 → 390 MB, RSS после загрузки 253 → 788 MB; на 2 GB RAM индексация батчем 32 убита OOM | ❌ |
| Работает без правок кода | подложенная как есть (mean pooling + префиксы USER2): MRR@10 0.511 против 0.605 (−0.094, значимо) | ❌ |
| Совместима со схемой | размерность 384 = `vec0 float[384]` | ✅ |

Рекомендация (§7): оставить USER2-small по умолчанию; добавить granite как **опциональный пресет** `EMBED_MODEL` с правильным пулингом, без префиксов и с автоматическим переиндексированием при смене модели. Попутная находка: **USER2-small int8** на русском не хуже fp32, вчетверо меньше и в 1.4–2 раза быстрее — кандидат в модель по умолчанию сам по себе (§5.5).

## 1. Где прокси использует модель

| Место | Что делает | Что важно для замены |
|---|---|---|
| `load_tokenizer` (`proxy.py` ~L248) | `tokenizer.json` через `tokenizers`, обрезка 512 токенов | длина в токенах зависит от токенизатора |
| `_embed` (~L257) | ONNX → выход `sentence_embedding`, если есть, иначе **mean pooling** → L2 | у обеих моделей ONNX отдаёт только `last_hidden_state`, значит всегда mean pooling |
| `embed_query` / `embed_document` (~L274) | **жёстко** префиксы USER2 `search_query: ` / `search_document: ` | granite обучена без префиксов |
| `vec_facts` (L309) | `vec0(user_id partition key, embedding float[384])` | обе модели — 384 |
| `backfill_vec` (~L435) | досчитывает векторы только для фактов **без** вектора | маркера модели нет: после смены модели старые векторы остаются и сравниваются с новыми запросами |
| гибридный поиск (~L1185) | FTS5 bm25 + вектор, RRF 1/(61+i), топ-15; запрос — `user_text[:2000]` | эмбеддинг вопроса считается на горячем пути, до запроса к LLM |
| `download_model.py` | репозиторий USER2 и ревизия `4a3caf0c…` зашиты; `MODEL_REVISION` из env | репозиторий не настраивается |

Векторный поиск в v5 выполняется только для **нового** вопроса (шаги агента берут закреплённую дельту), но для нового вопроса эмбеддинг стоит прямо в TTFT.

## 3. Что значит «идеальная замена» для этой архитектуры

Критерии выведены из устройства прокси и решений, принятых ранее:
1. **Русский не хуже.** Прокси русскоязычный: `MEMORY_POLICY`, промпт извлечения фактов, триггеры Context Bridge и оценки стиля — на русском; основной пользователь пишет по-русски.
2. **Другие языки — лучше.** Это и есть цель FR.
3. **Задержка ответа не растёт** — требование к архитектуре v5. Эмбеддинг нового вопроса стоит в TTFT.
4. **Домашний сервер без GPU:** модель на CPU, образ и RAM — в разумных пределах (тестовая машина: 2 vCPU, 2 GB RAM).
5. **Минимум правок и миграций:** та же размерность, предсказуемый переход для существующих баз.

## 4. Метод

Харнесс [`eval.py`](../bench/embeddings/eval.py) воспроизводит условия `proxy.py`: onnxruntime 1.18.1 на CPU, `intra_op_num_threads=2`, `tokenizers`, обрезка 512, L2-нормировка, косинус.

**Варианты:** `user2` (штатный: mean + префиксы), `user2_int8`, `granite` (CLS, без префиксов — как в карточке модели), `granite_int8`, `granite_asis` (granite, подложенная в текущий код без правок: mean + префиксы USER2).

**Наборы:**
1. **Доменный** ([`memory_set.py`](../bench/embeddings/memory_set.py)) — то, что делает прокси: найти факт о пользователе по его сообщению. 30 фактов по всем 14 предикатам в формате `vec_facts` (`predicate: object`, значения по-русски, как их извлекает прокси из русской переписки): 33 целевые записи — у фактов «какие языки я знаю» и «что раздражает на работе» правильных записей несколько, засчитывается любая — и 42 дистрактора того же вида, всего 75 записей. На каждый факт 5 запросов: `ru`, `ru2` (косвенный: «Куда сходить вечером в моём городе?» → `lives_in`), `en`, `uk` и один из `de` (14), `kk` (5), `tr` (4), `es` (1), `mix` (6, русский вперемешку с английским). 150 запросов. Метрики — MRR@10, Recall@k, nDCG@10; гибрид FTS5 + вектор + RRF — как в `get_smart_facts`.
2. **Публичные (MTEB):** RuBQ (русский retrieval; 300 запросов, корпус — релевантные + 4000 случайных документов), Wikipedia Retrieval Multilingual bg и de (одноязычный retrieval; 300 запросов, релевантные + 2500; русского в этом наборе нет), Tatoeba X→eng (кросс-языковой поиск переводов; 1000 пар, kaz 575, uzb 428).
3. **Скорость и ресурсы:** медиана 15 вызовов эмбеддинга одного вопроса (как `aembed_query`) на 40, 300 и 2000 символов; токены на 1000 символов по языкам; размер файлов; RSS после загрузки и пиковый; скорость индексации документов (батч 8).

Значимость — парный бутстреп разницы MRR@10 по запросам (10 000 повторов, 95% интервал, [`bootstrap.py`](../bench/embeddings/bootstrap.py)). «Значимо» ниже — интервал не содержит 0.

## 5. Результаты

### 5.1 Доменный набор (150 запросов, векторный поиск)

| Вариант | MRR@10 | R@1 | R@3 | R@5 | R@10 | nDCG@10 |
|---|---|---|---|---|---|---|
| `user2` (штатная) | 0.605 | 0.527 | 0.660 | 0.733 | 0.780 | 0.644 |
| `user2_int8` | 0.612 | 0.533 | 0.687 | 0.713 | 0.767 | 0.646 |
| `granite` | **0.652** | **0.547** | **0.693** | **0.793** | **0.900** | **0.708** |
| `granite_int8` | 0.597 | 0.493 | 0.647 | 0.747 | 0.853 | 0.653 |
| `granite_asis` (без правок кода) | 0.511 | 0.393 | 0.567 | 0.660 | 0.767 | 0.573 |

По всем запросам granite впереди на +0.048 MRR@10, но интервал [−0.025; +0.121] содержит 0: **в среднем по набору разница незначима**. Картина складывается из противоположных сдвигов по языкам:

|---|---|---|---|---|---|---|
| `ru` | 30 | **0.759** | 0.666 | 0.638 | 0.601 | ru + ru2: **−0.161** [−0.264; −0.058] |
| `ru2` (косвенные) | 30 | **0.844** | 0.616 | 0.518 | 0.432 | |
| `en` | 30 | 0.767 | 0.771 | 0.682 | 0.644 | +0.003 [−0.076; +0.085] |
| `uk` | 30 | 0.371 | **0.601** | 0.564 | 0.484 | **+0.230** [+0.035; +0.416] |
| `de` | 14 | 0.183 | **0.671** | 0.672 | 0.413 | de + kk + tr + es: **+0.414** [+0.248; +0.589] |

Сильнее всего granite проигрывает на **косвенных русских** запросах — там, где нужен смысл, а не совпадение слов. Типичные промахи granite (факт не в топ-5), которые USER2 находит:
- «Какую зелень я не ем?» → первым `likes: зелёный чай` вместо `dislikes: кинза`;
- «Какой режиссёр мне нравится?» → `dislikes: кинза` вместо `likes: фильмы Тарковского`;
- «Посоветуй телескоп для начинающего» → `dislikes: ранние подъёмы` вместо `interested_in: астрономия`;
- «Когда пора менять резину на зимнюю на моём кроссовере?» → `likes: осень` вместо `owns: Toyota RAV4`.

Гибрид (FTS5 + вектор, как в прокси) почти не отличается от чистого вектора (MRR 0.606 против 0.605 у USER2, 0.652 у granite): FTS находит релевантный факт в топ-5 лишь для 2.7% запросов — слова вопроса и факта почти никогда не совпадают ни между языками, ни между словоформами. Мультиязычность целиком лежит на модели эмбеддингов.

Токенизатор granite дробит русский на 18% сильнее, но экономнее на украинском (в 1.4 раза), казахском (в 1.8), немецком (в 2.1) и китайском (в 5.2 раза). Поэтому на немецком корпусе granite индексирует так же быстро, как USER2, хотя сама модель втрое больше. На русском — почти вдвое медленнее.

На машине с 2 GB RAM индексация публичных корпусов granite fp32 батчем 32 была убита OOM-killer'ом; с батчем 8 прошла. Прокси индексирует короткие факты (`predicate: object`) батчами по 64 — там это не проблема, но запас памяти на маленьких серверах уменьшается на ~0.5 GB.

### 5.5 Квантование int8

- **USER2 int8** не отличается от fp32 на доменном наборе (+0.007 [−0.016; +0.031]), на русских запросах (+0.002) и на RuBQ (−0.011, незначимо); немного теряет на болгарском и немецком (−0.02…−0.03, значимо). При этом файл вчетверо меньше (35 MB), RSS 108 MB, эмбеддинг вопроса в 1.4–2 раза быстрее.
- **granite int8** теряет заметно: доменный набор 0.597 (ниже USER2 fp32), русский −0.224 к USER2, RuBQ 0.799 (−0.066, значимо). Немецкий сохраняется.

То есть быстрый granite (int8) — уже не лучше USER2 в среднем, а медленный (fp32) — не укладывается в бюджет задержки и памяти.

### 5.6 Подстановка без правок кода (`granite_asis`)

Если положить granite в `MODEL_DIR` вместо USER2, прокси будет считать mean pooling и добавлять префиксы USER2. Результат хуже штатной модели: MRR@10 0.511 против 0.605 (−0.094 [−0.163; −0.023]), на русском −0.286, на английском −0.123; выигрыш остаётся только на немецком/казахском/турецком (+0.165). Кроме того, `backfill_vec` не пересчитает уже сохранённые векторы USER2 — запросы granite будут сравниваться с векторами другой модели, пока не выполнить `manage.py reindex` и перезапуск.

## 6. Оценка гипотезы

Сводка — в §0. По каждому критерию «идеальной замены» из §3:
1. **Русский не хуже — нет.** Значимый проигрыш на доменном наборе (особенно на косвенных запросах) и на Tatoeba; паритет только на фактоидном RuBQ.
2. **Другие языки лучше — да,** с большим запасом на украинском, немецком, турецком, европейских языках и китайском.
3. **Задержка не растёт — нет:** эмбеддинг вопроса в 1.2–1.8 раза медленнее, чем дольше вопрос, тем больше разница (+12 мс на типичном вопросе в 300 символов, +133 мс на длинном), что противоречит требованию v5. int8 укладывается по задержке, но теряет качество.
4. **Ресурсы — хуже:** втрое больше файл и RSS.
5. **Без правок — нет:** нужен CLS-пулинг, отключение префиксов, настраиваемый репозиторий и переиндексация.

granite — сильная **мультиязычная** модель, но для архитектуры memory-proxy, где основной язык — русский, она не идеальна. Правильная постановка: не «заменить», а «дать выбор».

## 7. Рекомендация и план интеграции

**Решение (предложение):** по умолчанию остаётся USER2-small; granite — опциональный пресет для тех, кто пишет на украинском, немецком, других европейских языках или смешивает языки.

1. **Пресет модели** `EMBED_MODEL` = `user2` (по умолчанию) | `granite-multilingual`. Пресет задаёт репозиторий, закреплённую ревизию, файл ONNX, пулинг (`mean` | `cls`), префиксы запроса и документа. Ручная настройка для других моделей — `EMBED_REPO`, `EMBED_POOLING`, `EMBED_QUERY_PREFIX`, `EMBED_DOC_PREFIX` (размерность обязана быть 384, проверка при старте).
2. **`_embed`:** пулинг по конфигурации; выход `sentence_embedding`, если он есть в ONNX, по-прежнему в приоритете. `embed_query` / `embed_document` берут префиксы из конфигурации.
3. **Маркер модели в базе:** хранить идентификатор модели (репозиторий + ревизия + пулинг + префиксы). При несовпадении на старте — `DELETE FROM vec_facts` и `backfill_vec()` с предупреждением в логе (то же, что `manage.py reindex`, но автоматически). Факты короткие, переиндексация тысяч фактов — секунды-минуты в фоне при старте.
4. **Образ:** `download_model.py` читает пресет; в Dockerfile `ARG EMBED_MODEL=user2`. Отдельный тег образа для мультиязычной сборки (например, `vX.Y.Z-multilingual`) — модель и токенизатор добавляют к образу ≈ 270 MB.
5. **Ограничить стоимость эмбеддинга вопроса:** `EMBED_QUERY_MAX_CH` (по умолчанию 2000, как сейчас); для granite разумно 1000 — по оценке ~120–140 мс вместо ~290 мс на длинном вопросе (не замерялось).
6. **Отдельно рассмотреть USER2 int8 по умолчанию** (§5.5): то же качество на русском, образ на ~100 MB легче, вопрос считается быстрее. Перед переключением — маркер модели из п. 3 (векторы fp32 и int8 близки, но не идентичны).
7. **Тесты:** пулинг и префиксы по пресету (заглушка ONNX), смена маркера → переиндексация, неверная размерность → ошибка старта; бенчмарк [`../bench/embeddings/`](../bench/embeddings/README.md) — ручной, вне CI.

## 8. Модель — не единственное, что мешает мультиязычности

Даже с мультиязычной моделью часть прокси останется русскоязычной:
- триггеры Context Bridge и блока истории (`CROSS_CHAT_TRIGGERS`, `proxy.py` L129–131; триггер истории ~L590, ~L1275) — только русские слова;
- слова похвалы и критики для оценки стиля (`PRAISE` L134, `CRITIQUE` L135–136);
- `MEMORY_POLICY` (L139+) и промпт извлечения фактов (`build_extract_payload`) написаны по-русски — модель понимает их на любом языке, но значения фактов приходят на языке переписки;
- FTS5 без стемминга для других языков: в гибриде он и так почти ничего не добавляет (§5.1).

Для полноценной мультиязычности это отдельные задачи: вынести триггеры и слова оценки в настраиваемые списки с наборами для нескольких языков и написать политику и промпт на английском (нейтральном для моделей).

## 9. Ограничения исследования

- Доменный набор небольшой: 150 запросов, для `de`/`kk`/`tr`/`es`/`mix` — от 1 до 14. Выводы по этим языкам опираются ещё на публичные наборы и Tatoeba.
- Значения фактов в доменном наборе — по-русски (так прокси извлекает их из русской переписки). Сценарий «вся переписка на другом языке» покрывают одноязычные Wikipedia bg/de, а не доменный набор.
- Корпуса публичных наборов урезаны (релевантные + 2500–4000 случайных документов) ради времени на 2 vCPU; абсолютные значения выше, чем на полных корпусах MTEB, сравнение моделей между собой корректно.
- Обрезка 512 токенов, как в прокси; длинные контексты granite (до 32k) не проверялись — прокси их не использует.
- Скорость измерена на 2 vCPU; на другом CPU абсолютные миллисекунды будут другими, соотношения — близкими.
- Другие кандидаты не проверялись. По опубликованным данным: `deepvk/USER2-base` сильнее USER2-small на русском (MTEB-rus 61.12 против 58.32), но тоже только русский и английский; `intfloat/multilingual-e5-small` в карточке granite уступает ей на мультиязычном retrieval (50.9 против 60.3).
