## 0. Коротко

Все найденные проблемы (P1–P13, всплески задержки после сжатия, промахи кеша в агентном цикле, 400 и молчаливая обрезка на переполнении) — следствия трёх архитектурных решений v4.8. v5 меняет все три. Главное правило: **промпт к модели только растёт**. Префикс между ходами не меняется, кроме редких смен эпохи; новую эпоху готовят и прогревают в фоне.

| | v4.8 | v4.9 + прогрев | **v5** |
|---|---|---|---|
| Пересчёт на ход, до переполнения (ток.) | 1309 | 1309 | **277** |
| Пересчёт на ход, после переполнения | 3376 | 1235 | **278** |
| Худший ход после переполнения | 3453 | 1353 | **304** |
| TTFT, M2 Pro, после переполнения | 11.0 с | 6.1 с | **1.4 с** |
| TTFT, CPU ноутбука, после переполнения | 1.8 мин | 65 с | **15 с** |
| Фон на 60 ходов (ток.) | 0 | 34 437 | 43 994 |

v5 рассчитан на **одного пользователя с любыми OpenAI-совместимыми клиентами** (§12); командный режим — отдельный дизайн.

Задержка для пользователя уменьшается в 4–8 раз на всех профилях и не растёт ни на одном ходу. Цена — фоновая работа (+28% к v4.9). По решению «нагрузка не проблема, если в фоне» это допустимо.

## 1. Три корневые причины

### R1. Промпт каждый раз собирается заново из изменчивых частей
`forward` на каждый запрос заново считает `<memory>` и вставляет его в **последнее** сообщение пользователя. Блок `<memory>` состоит из:
- фактов (векторный поиск по текущему вопросу);
- эмоций (затухают со временем, значит меняются каждую минуту);
- примеров стиля (`ORDER BY RANDOM()`);
- иногда цитат из других чатов.

Из-за этого:
- в прошлом сообщении пользователя `<memory>` пропадает, а в новом появляется другой. Кеш KV ломается на предпоследнем сообщении, и каждый ход пересчитываются прошлый ответ и вопрос (≈1300 ток. даже без сжатия);
- в агентном цикле тот же вопрос получает на каждом шаге новый `<memory>` (P8), и кеш ломается на каждом шаге;
- `compress()` переписывает начало истории, после чего пересчитывается всё (всплески P5/P6).

**Принцип, который нарушен:** промпт — это функция от времени и случайности, а не от истории чата.

### R2. Бюджет не привязан к реальной модели
Решения принимаются по счётчику сообщений (`>10`, `KEEP_RECENT=8`) и фиксированному `COMPRESS_AT=16000`. Реальный `n_ctx` модели прокси не знает (P11–P13). В итоге:
- короткий чат из длинных сообщений получает 400 от llama.cpp;
- Ollama молча режет начало, включая system и вопрос пользователя в цикле инструментов.

### R3. Дорогая работа, меняющая состояние, идёт в горячем пути
Сжатие, а в v4.9 ещё и суммаризация считаются синхронно внутри запроса пользователя. Последствия:
- либо пользователь ждёт LLM-саммари;
- либо (вариант без прогрева в v4.9) получает худший ход 9163 ток. пересчёта сразу после переключения окна.

Перестройка контекста — это событие, которое можно подготовить заранее, а не побочный эффект ответа.

## 2. Принципы v5

1. **Только дописываем (append-only).**
   - `prompt(t+1)` начинается байт-в-байт с `prompt(t)` до конца прошлого ответа.
   - Исключения: смена эпохи (§4), правка или перегенерация сообщения в клиенте.
2. **Детерминизм.**
   - Сборка промпта — чистая функция от `(история, состояние чата)`.
   - Никаких `RANDOM()`, `time.time()` или затухания внутри сборки. Всё изменчивое замораживается при создании эпохи или при закреплении дельты.
3. **Бюджет в токенах реальной модели.**
   - Счётчиков сообщений нет.
   - `B = min(COMPRESS_AT, 0.9·n_ctx − ANSWER_RESERVE − tools)` (§4.7 v4.9).
4. **Горячий путь не ждёт LLM.**
   - Всё LLM-ное (саммари, профиль, прогрев) идёт в фоне и уступает пользовательским запросам (§5.12).
   - Если фон не успел, срабатывает дешёвый детерминированный откат без LLM.
5. **Ничего не теряется молча.**
   - Отрезанное остаётся в БД и доступно через recall (§5.9).
   - Если не помещается даже текущий ход, это явный ответ в чат (`OVERSIZE`), а не обрезка на стороне бэкенда.

## 3. Компоненты

```
             ┌───────────── горячий путь (≈1–3 мс) ──────────────┐
запрос ──▶ Router ──▶ ChatState.load ──▶ Assembler ──▶ Guard ──▶ Forwarder ──▶ бэкенд
             │            ▲                   │          │ 400 → учесть n_ctx,
             │            │                   │          │ один повтор
             │            │        delta = MemoryDelta(вопрос) − уже в окне
             │            │                   │
             └── ответ ──▶ Recorder ──▶ (факты, эмоции, стиль: как в v4.8)
                          │
                          ▼ (если окно > EPOCH_PREP_AT·B)
             ┌──────────── фон, с вытеснением ────────────┐
             │ EpochPlanner: новая граница k, саммари,    │
             │ профиль → прогрев префикса → ready         │
             └────────────────────────────────────────────┘
```

| Компонент | Ответственность | Чего НЕ делает |
|---|---|---|
| **Router** | `user_id`, `chat_id`, команды, служебные запросы OWUI (`### Task:` → пропуск памяти) | — |
| **ChatState** | эпоха, закреплённые дельты, готовая следующая эпоха; в SQLite | не ходит в LLM |
| **Assembler** | чистая функция `(история, ChatState, delta) → messages` | не трогает БД, не знает про HTTP |
| **MemoryDelta** | факты и recall для текущего вопроса минус то, что уже в окне | не меняет прошлые сообщения |
| **Guard** | инварианты I1–I6 v4.9, бюджет `B`, откат L1/L3, `OVERSIZE` | — |
| **Forwarder** | только транспорт: стрим, ретрай на 400, учёт `n_ctx` | не меняет содержимое (сейчас это смешано в `forward`, ~200 строк) |
| **EpochPlanner** | фон: граница, саммари (map-reduce §5.10), профиль, прогрев | не блокирует запрос |

Assembler — чистая функция, поэтому свойство «только дописываем» проверяется юнит-тестом: собрать ходы `t` и `t+1` и сравнить общий префикс.

## 4. Устройство промпта

```
[system]  исходный system клиента + MEMORY_POLICY            ← не меняется никогда
[user k]  <summary>…</summary>                               ← только при смене эпохи
          <profile>факты-ядро, эмоции, примеры стиля</profile>
          текст сообщения k
[asst]    …
[user]    <memory>дельта, закреплённая за этим сообщением</memory> текст
[asst]    …
  …                                                          ← всё это — повтор байт-в-байт
[user t]  <memory>новая дельта</memory> текст                 ← новое: ≈280 ток.
```

### 4.1 Эпоха
Эпоха — неизменяемая запись `(epoch_id, cut_hash, summary, profile, created)`. Она хранит:
- `cut_hash` — хеш первого сообщения окна; режем только по границе хода, по правилам §4.3 v4.9;
- `summary` — саммари всего, что до `k` (инкрементально, по хеш-цепочке §5.3 v4.9);
- `profile` — снимок долгоживущей памяти на момент эпохи: топ-N фактов по важности, эмоции с уже применённым затуханием, 3 примера стиля, выбранных детерминированно (`ORDER BY hash(epoch_id, id)`). До `PROFILE_CH` = 1500 символов.

Блок `<profile>` стоит в начале окна и в пределах эпохи не меняется. Поэтому:
- затухание эмоций и ротация стиля работают с шагом эпохи, а не запроса — для человека разницы нет;
- новый факт, извлечённый на ходе `t`, сразу попадает в дельты (§4.2), а в профиль — при следующей смене эпохи.

### 4.2 Закреплённая дельта
На каждый новый вопрос пользователя:
1. Подобрать факты под вопрос (как сейчас) и recall из отрезанной части чата (§5.9).
2. **Вычесть** то, что уже видно модели: профиль и дельты в окне (по `fact_id`). Обрезать до `DELTA_CH` = 300 символов.
3. Сохранить: `pinned[(chat_id, msg_hash)] = delta`.
4. Во всех следующих запросах вставлять в это сообщение **ту же строку**.

Следствия:
- **Агентный цикл (P8).** Шаги с одним и тем же вопросом находят дельту по `msg_hash` и получают ту же строку. Кеш не ломается, `embed_query` на шаге не вызывается (−28 мс на шаг). Отдельный кеш памяти на агентный ход (v4.9 §4.6) больше не нужен.
- **Перегенерация ответа** — тот же `msg_hash`, та же дельта.
- **Правка вопроса** — новый хеш, новая дельта; дальше снова только дописываем.
- **Факт сказан в чате** — он и так в окне, дублировать его не нужно. Вычитание это учитывает: факты из сообщений внутри окна не выдаются.

`msg_hash = sha1(role, content_без_нашей_вставки, индекс_хода)`. Индекс нужен, чтобы два одинаковых «ок» не склеились.

### 4.3 Смена эпохи (единственное место, где префикс меняется)

| Порог | Значение по умолчанию | Действие |
|---|---|---|
| `EPOCH_PREP_AT` | 0.7·B | фон: EpochPlanner готовит следующую эпоху с окном ≈ `EPOCH_TARGET` = 0.5·B (§5.11 v4.9) |
| `EPOCH_AT` | 1.0·B | горячий путь: если эпоха готова и прогрета — переключиться (стоимость как у обычного хода) |
| > B, эпоха не готова | — | откат без LLM: L1-элизия старых tool-выводов, затем L3 (отрезать старые ходы + recall). Только в этом редком случае ход дороже обычного |

`EPOCH_AT` = 1.0 вместо 0.85 вдвое снизило фон (5 смен вместо 8, 44k вместо 71k ток.). Пересчёт для пользователя не изменился (средний 278, максимум 304).

Элизия старых tool-выводов (L1 v4.9) — это переписывание прошлого. В v5 её **делают только при смене эпохи**, а не на каждом запросе: иначе она ломает префикс так же, как сейчас `<memory>`.

### 4.4 Прогрев и порядок в бэкенде
Подготовленный префикс новой эпохи отправляется в бэкенд как `max_tokens=1` (llama.cpp `cache_prompt`, Ollama `num_predict=1`), когда пользователь не ждёт ответа.
- В llama.cpp с `-np 1 --cache-ram N` прошлый префикс уходит в RAM-кеш и не теряется: если пользователь успеет написать до переключения, его ход всё равно попадёт в кеш. Это проверено ещё в v4.9.
- Служебные запросы Open WebUI (заголовок, теги, follow-up) — отдельные промпты, которые с `-np 1` вытесняют слот. Рекомендация в README: llama.cpp `-np 2` или `--cache-ram`; у Ollama `OLLAMA_NUM_PARALLEL=2`.

### 4.5 Бюджет и переполнение на коротких чатах (P11–P13)
Никаких «≤10 сообщений». Guard считает токены собранного промпта и сравнивает с `B`:
- **`n_ctx`** берётся по порядку: `CONTEXT_LIMIT` из env → llama.cpp `/props` → Ollama `/api/show` + `options.num_ctx`, который прокси **сам выставляет** (иначе Ollama молча держит 2–4k) → самообучение по `400 exceed_context_size_error` (один прозрачный повтор).
- **Порядок жертв** — §4.7 v4.9: старые ходы → профиль/дельты → саммари → (никогда) текущий ход и system.
- **Текущий ход сам больше `B`** — `OVERSIZE=truncate` (середина длинных tool-выводов и вложений с пометкой) или `reject` (понятный ответ в чат).

## 5. Хранение (схема v4 вместо v4.9-шной)

```sql
CREATE TABLE chat_epochs(
  user_id TEXT, chat_id TEXT, epoch_id INTEGER, cut_hash TEXT,
  summary TEXT, profile TEXT, state TEXT,       -- 'active' | 'ready' | 'preparing'
  prefix_tokens INTEGER, created REAL,
  PRIMARY KEY(user_id, chat_id, epoch_id));
CREATE TABLE pinned_deltas(
  user_id TEXT, chat_id TEXT, msg_hash TEXT, delta TEXT, fact_ids TEXT, created REAL,
  PRIMARY KEY(user_id, chat_id, msg_hash));
CREATE TABLE chat_chain(                        -- привязка запроса к чату по префиксу истории (§12.4)
  user_id TEXT, chat_id TEXT, pos INTEGER, msg_hash TEXT, parent_hash TEXT,
  PRIMARY KEY(user_id, chat_id, pos, msg_hash));
CREATE INDEX ix_chain_head ON chat_chain(user_id, msg_hash) WHERE pos <= 1;
```

- Таблица `summaries` из v4.9 (§5.4) становится полем эпохи. Хеш-цепочка остаётся для инкрементальной суммаризации.
- Чистка: дельты старше активной эпохи можно удалять (их сообщения уже за границей). `/forget chat` чистит обе таблицы.
- Миграция: таблицы пустые. Чат без эпохи начинает с эпохи 0 (`k=0`, без саммари, профиль строится при первом запросе).

## 6. Почему это не замедляет ответ

1. **Горячий путь дешевле, чем в v4.8:**
   - чтение эпохи и дельт — 2 запроса по ключу;
   - векторный поиск — только для **нового** вопроса, не на шагах агента;
   - сборка — конкатенация.
   Прокси v4.9 тратил 0.6–1.9 мс (p95 3 мс); v5 не больше.
2. **Пересчёт на модели падает в 4.7× ещё до переполнения:** пропадает поломка на предпоследнем сообщении (R1).
3. **Смена эпохи бесплатна для пользователя:** новый префикс уже в кеше. Худший ход — 304 ток. против 3453 в v4.8.
4. **Промпт длиннее.** Закреплённые дельты накапливаются (~95 ток./ход), окно в среднем 12k против 3.6k у v4.8. Это учтено в модели скорости (pp и tg падают с глубиной):
   - полный ответ из 480 токенов всё равно быстрее на всех профилях (таблица ниже);
   - декод на 4090 +0.1 с — в пределах шума.

### 6.3 Проверка на живом llama.cpp
`validate_v5.py`: Qwen2.5-0.5B, CPU, уменьшенный масштаб (бюджет 2000 ток.), 16 ходов, 6 смен эпохи с прогревом.
- Предсказанный пересчёт совпал с `timings.prompt_n` сервера в **16 из 16** запросов.
- На ходах со сменой эпохи пересчёт 158–178 ток. — меньше обычного хода (364–411), то есть смена эпохи для пользователя незаметна.

| **A** | Бюджет от `n_ctx` + самообучение + `OVERSIZE`; Guard с I1–I6; резка по ходам; Forwarder отделён от сборки; **не вставлять лишние system** (ошибка шаблона на 6/32, §11.1); `ModelProfile` + токены от бэкенда (§11.2) | нет | низкий, чинит 400, молчаливую обрезку и падения на Mistral/Gemma 2/Qwen3.5 |
| **B** | Assembler + `ChatState`; эпоха 0 с `<profile>`; закреплённые дельты; детерминированный стиль; `CONTEXT_MODE` | нет | средний; главный выигрыш по скорости (4.7× до переполнения) |
| **C** | EpochPlanner: саммари (map-reduce), прогрев, вытеснение; L1 только на смене эпохи | да, в фоне | средний |
| **D** | Recall из отрезанного → в дельту | нет | низкий |
| **U** | Однопользовательский режим (§12): `USER_MODE=single`, `OWNER`, `manage.py merge`, чат по префиксу истории, служебные запросы любых клиентов, проброс `/v1/*`. Можно делать раньше B/C/D | нет | низкий |

Тесты, кроме перечисленных в v4.9:
- **префикс** — ходы `t` и `t+1` без смены эпохи, `prompt(t)` — префикс `prompt(t+1)` (property-тест на случайных историях с tool calls);
- **агент** — 15 шагов одного хода дают одинаковую дельту и ни одного вызова `embed_query` после первого;
- **регенерация и правка** — проверка хешей дельт;
- **смена эпохи без готовой эпохи** — откат L3 укладывается в `B`;
- **детерминизм** — две сборки подряд дают байт-в-байт одинаковый результат при сдвинутом `time.time()`.

## 10. Оговорки

- Расчёты — модель `pp(d) = pp0/(1+d/D)` и опубликованные замеры. Абсолютные секунды ориентировочные, отношения надёжнее. Совпадение предсказанного пересчёта с сервером: 59/60 (v4.9) и 16/16 (v5).
- Если клиент сам меняет историю (RAG Open WebUI в последнем сообщении, удаление вложений), префикс ломается на стороне клиента. v5 это переживает (новый хеш → новая дельта), но выигрыш на таких ходах меньше.
- Облачные API с префикс-кешем (OpenAI, Anthropic, DeepSeek) выигрывают от того же принципа и в деньгах: кешированные токены дешевле.

## 11. Универсальность: любые модели и шаблоны чата

Прокси работает на уровне OpenAI `messages`, а шаблон применяет бэкенд (llama.cpp `--jinja`, vLLM, LM Studio; у Ollama свои Go-шаблоны). Значит, прокси не должен знать про `<|im_start|>`. Шаблоны различаются только тем, **что они делают с сообщениями**.

### 11.1 Проверка 32 реальных шаблонов ([`../bench/templates/`](../bench/templates/))
Шаблоны из `llama.cpp/models/templates`: Qwen 2.5/3/3.5/QwQ, Gemma 2/4, Llama 3.1/3.2/3.3, Mistral Nemo/Small 3.2/Ministral 3, DeepSeek R1/V3.1/V3.2, gpt-oss, GLM, Kimi, Phi, Granite, Hermes, GigaChat и др. Рендер через jinja2 (как HF); сравнивался промпт хода `t` и `t+1`.

| Проверка | ok | теряется только хвост (последний ответ) | ломается история | ошибка шаблона |
|---|---|---|---|---|
| обычный чат | 21 | 8 (reasoning: из истории вырезается `<think>`) | 2 | 1 |
| шаг агента (+ tool result) | 22 | 7 | 1 | 2* |
| следующий ход после tool calls | 19 | 6 | 5 | 2* |
| смена даты | 29 | — | 2 | 1 |

\* 1 шаблон (Kimi-K2-Thinking) — артефакт песочницы jinja2 (`list.append`), не ошибка шаблона.

Что ломает префикс **на стороне шаблона**:
- **Mistral Nemo** переносит system в **последнее** сообщение пользователя → поломка на предпоследнем вопросе каждый ход (как `<memory>` в v4.8).
- **Mistral Small 3.2 / Nemo** вставляют список инструментов `[AVAILABLE_TOOLS]` перед последним вопросом → определения инструментов пересчитываются каждый ход.
- **Llama 3.2, gpt-oss** пишут сегодняшнюю дату (`strftime_now`) в system → полный пересчёт раз в сутки.
- **Reasoning-модели** (Qwen3.5, QwQ, R1, DeepSeek V3.2, GLM-4.7, MiniMax-M2, Gemma 4, Nemotron) вырезают размышления из прошлых ответов → пересчитывается последний ответ. Это дёшево и заложено самой моделью; Qwen3.5 после хода с инструментами вырезает размышления и у шагов агента.
- **Ограничения ролей:** Gemma 2 не поддерживает system; Mistral требует строгого чередования user/assistant; Ministral 3, Qwen3.5 и Apertus запрещают system не в начале.

**Найденная ошибка v4.8:** `compress()` вставляет второй system (`[РАНЕЕ]`) в середину, а `inject_memory` добавляет system, если его нет. На **6 из 32** шаблонов (Qwen3.5, Gemma 2, Mistral Nemo, Mistral Small 3.2, Ministral 3, Apertus) это даёт ошибку шаблона. После переполнения чат на этих моделях перестаёт отвечать ([`../bench/templates/v48_out.txt`](../bench/templates/v48_out.txt)).

### 11.2 Правила v5, которые делают прокси шаблоно-независимым
1. **Не добавлять сообщения и не менять роли.** Профиль, саммари и дельты вставляются только в `content` уже существующих сообщений user (v5 так и устроен). Тогда строгие шаблоны (чередование, system только первым) не ломаются.
2. **`content` может быть списком** (картинки, файлы): вставлять отдельной text-частью, а не через f-строку. Сейчас v4.8 для таких сообщений память просто пропускает.
3. **Профиль возможностей модели** (`ModelProfile`) **определяется автоматически, не по имени модели:**
   - llama.cpp: `POST /apply-template` на синтетических диалогах (те же проверки, что в [`check.py`](../bench/templates/check.py)). vLLM: `/tokenize` с `messages`. Определяется: разрешён ли system; стабилен ли он по позиции; строгость чередования; стабильность tools; зависимость от даты.
   - Стратегии по результату: `system_mode = native | first_user` (для Gemma 2 и Mistral Nemo политика и system клиента сворачиваются в первое сообщение user — стабильно для любого шаблона); дата — `chat_template_kwargs.date_string`, закреплённая на эпоху (Llama 3.x).
   - Бэкенды без рендера (Ollama, облака): по умолчанию безопасная стратегия (`first_user` не нужен, ничего не добавляем) + наблюдение за кешем по факту.
   - Переопределение: `MODEL_PROFILES` (JSON: regex имени модели → поля профиля).
4. **Токены** считаются токенизатором бэкенда: llama.cpp и vLLM `/tokenize`, иначе оценка по символам с **самокалибровкой** по `usage.prompt_tokens` для каждой модели и запасом 10%. Для кириллицы токенизаторы расходятся в разы, одна константа на всех не годится.
5. **Лимит контекста** (§4.5) по бэкендам: llama.cpp `/props` (`n_ctx` делится на число слотов `-np`), vLLM `/v1/models` `max_model_len`, Ollama `/api/show` + фактический `num_ctx` (через `/v1` его не передать, нужен `OLLAMA_CONTEXT_LENGTH` или Modelfile), облака — таблица или env. Плюс самообучение по 400.
6. **Reasoning:** в БД, факты и примеры стиля сохраняется ответ **без** `<think>…</think>` / `reasoning_content`. Иначе на моделях без парсера рассуждений размышления попадут в память.
7. **Монитор кеша:** ожидаемое переиспользование (общий префикс с прошлым запросом) сравнивается с фактическим (`timings.prompt_n` у llama.cpp, `usage.prompt_tokens_details.cached_tokens` у vLLM и облаков). Устойчивое расхождение → предупреждение в лог и `/stats`: «шаблон модели X ломает префикс на позиции …».
8. **Служебные LLM-задачи** (извлечение фактов, саммари): `response_format` / `json_schema` там, где бэкенд умеет (llama.cpp, vLLM, Ollama, LM Studio), плюс толерантный парсер. Отдельная `EXTRACT_MODEL`, если основная модель слабая.

### 11.3 Чего прокси не исправит
- Перенос tools перед последним вопросом (Mistral) — только через свой шаблон в бэкенде (`--chat-template-file`). Прокси может показать это в мониторе кеша.
- Вырезание размышлений reasoning-моделями — свойство модели, стоит около одного ответа на ход.

## 12. Пользователи и клиенты: v5 — однопользовательский режим

**Решение:** v5 проектируется и тестируется для **одного пользователя**, который работает из **любых OpenAI-совместимых клиентов**: Open WebUI, LibreChat, SillyTavern, Cline/Roo/Continue, Aider, скрипты и curl. Командный режим (несколько людей, роли, общая и личная память, изоляция) будет отдельным дизайном.

### 12.1 Почему не оставить как в v4.8
В v4.8 пользователь определяется по `X-OpenWebUI-User-Id` или полю `user`. Для одного человека с несколькими клиентами это **вредно**:
- Open WebUI с заголовками пишет память под UUID, а Cline без заголовков — под `default`. Один человек получает две несвязанные памяти.
- Некоторые клиенты заполняют поле `user` чем попало (имя сессии, имя персонажа, ID установки). Память дробится без ведома пользователя.
- Чтобы память была общей, сейчас нужно знать про `ENABLE_FORWARD_USER_INFO_HEADERS`, `reassign` и `TRUST_USER_HEADER`.

### 12.2 Как устроено в v5
- **Один владелец.** Все запросы, прошедшие проверку ключа, относятся к пользователю `OWNER` (по умолчанию `default`).
  - Заголовки `X-OpenWebUI-User-*` и поле `user` **игнорируются** для идентификации.
  - Поле `user` пробрасывается в бэкенд как есть.
- **Доступ:** один `API_KEY`. Рекомендован всегда; без него при старте пишется предупреждение (как сейчас).
  - `API_KEYS` в однопользовательском режиме не нужен.
  - Если он задан, все ключи ведут к `OWNER`. Это удобно, чтобы выдать каждому клиенту свой ключ и отзывать их по одному. При старте в лог пишется, сколько ключей.
- **Схема БД не меняется.** Колонка `user_id` остаётся во всех таблицах (включая новые `chat_epochs`, `pinned_deltas`) и всегда равна `OWNER`. Командному режиму потом не понадобится миграция, только логика идентификации.
- **Код v4.8 для нескольких пользователей** (`resolve_user` с заголовками, `TRUST_USER_HEADER`, ключ = пользователь) **остаётся** за `USER_MODE=multi` в состоянии «как в v4.8», без развития до отдельного командного дизайна. В README будет раздел «Несколько пользователей»: как включить `USER_MODE=multi`, `ENABLE_FORWARD_USER_INFO_HEADERS` в Open WebUI, персональные ключи `API_KEYS`, ограничения доверия к заголовкам. **По умолчанию всегда `USER_MODE=single`, `OWNER=default`.**
- Обратная совместимость с персональными ключами не требуется: ранний MVP, `API_KEYS` ни у кого не настроены.

### 12.3 Переход с v4.8
В базе могут уже быть данные под несколькими `user_id` (`default` и UUID из Open WebUI).
- При старте в `single` прокси считает `user_id` с данными. Если кроме `OWNER` есть другие, в лог пишется предупреждение со списком и командой. Автоматически ничего не сливается.
- Новая команда **`manage.py merge --into <owner>`** переносит всё к владельцу:
  - сообщения и чаты — как есть;
  - эмоции и примеры стиля — объединяются;
  - факты — конфликты однозначных предикатов («живёт в …») решаются **по свежести**: актуальным остаётся последний `valid_from`, старый закрывается `valid_to` (история сохраняется);
  - векторы пересчитываются (`reindex`).
  
  Перед слиянием делается резервная копия через `conn.backup()`.

### 12.4 Определение чата для любых клиентов
Без `X-OpenWebUI-Chat-Id` v4.8 берёт хеш первого сообщения пользователя. Проблемы:
- два разных чата, начатых с «привет», склеиваются;
- у агентных клиентов первое сообщение — шаблон с окружением, и разные задачи с похожим началом тоже склеиваются.

v5 привязывает запрос к чату **по префиксу истории**:
- **Хеш-цепочка.** Для каждого известного чата хранится цепочка хешей его сообщений: те же `msg_hash`, что для закреплённых дельт (§4.2); основа — хеш system и первого вопроса.
- **Выбор чата.** Запрос относится к чату, чья цепочка — **самый длинный префикс** присланной истории.
  - Два «привет»-чата совпадают только до первого ответа ассистента. Со второго хода каждый находит свой чат.
  - На первом ходе (только system + «привет») создаётся новый чат, если не найден чат, у которого префикс **совпадает целиком** и нет продолжения. Так же поведёт себя перегенерация первого ответа.
- **Ветки.** Если клиент перегенерировал ответ или правил сообщение посередине, история совпадает до точки правки, и дальше начинается **ветка того же чата**. Факты, эпоха и дельты до точки правки переиспользуются.
- **Заголовки клиентов** имеют приоритет, если есть: список имён в `CHAT_ID_HEADERS` (по умолчанию `X-OpenWebUI-Chat-Id`). Остальные клиенты работают по префиксу без настройки.
- **Стоимость:** поиск по индексу `(user_id, hash первого вопроса)` плюс сравнение цепочки — доли миллисекунды. Векторный поиск не нужен.

### 12.5 Что ещё нужно для «любого клиента»
- **Служебные запросы клиентов.** Генерация заголовков, тегов и подсказок есть не только у Open WebUI. Обработка такая:
  - `SERVICE_PATTERNS` выносится в настройку, к нему добавляются известные шаблоны LibreChat и SillyTavern.
  - Добавляется эвристика: запрос без истории + малый `max_tokens` + фраза-инструкция.
  - Такие запросы проходят без памяти и без записи в БД.
- **Прозрачный проброс.** Прокси обслуживает только `/v1/chat/completions` и `/v1/models`. Клиенты, которые через тот же адрес ходят в `/v1/embeddings`, `/v1/completions`, `/tokenize`, сейчас получают 404. В v5 неизвестные `/v1/*` проксируются в бэкенд без изменений (с проверкой ключа).
- **Обёртки агентных клиентов.** Cline, Roo и Aider оборачивают вопрос в свои теги и добавляют окружение (`<environment_details>`, списки файлов).
  - Извлечение фактов и поиск памяти работают по тексту пользователя без этих блоков (`CLIENT_STRIP_PATTERNS`).
  - Такие запросы чаще классифицируются как `technical`, и память не подставляется. Это ожидаемое поведение, как сейчас.
- **Слэш-команды** распознаются только как точное сообщение. Если клиент оборачивает текст, команда не сработает и уйдёт в модель. Это безопасно; в README будет указано.
- **Не входит в v5:** нативный API Ollama (`/api/chat`) и Anthropic (`/v1/messages`). Прокси говорит на OpenAI API, а такие клиенты работают с бэкендом напрямую. Возможное расширение.

### 12.6 Настройки
| Переменная | По умолчанию | Смысл |
|---|---|---|
| `USER_MODE` | `single` | `single` — один владелец; `multi` — поведение v4.8 (заморожено до отдельного дизайна) |
| `OWNER` | `default` | `user_id` владельца в `single` |
| `CHAT_ID_HEADERS` | `X-OpenWebUI-Chat-Id` | заголовки с ID чата, по приоритету |
| `SERVICE_PATTERNS` | встроенный список | дополнительные маркеры служебных запросов |
| `CLIENT_STRIP_PATTERNS` | встроенный список | обёртки агентных клиентов, вырезаемые перед анализом |
| `PASSTHROUGH` | `1` | проброс неизвестных `/v1/*` в бэкенд |

### 12.7 Тесты
- Запросы с разными `X-OpenWebUI-User-Id`, полем `user` и без них дают одну и ту же память `OWNER`.
- Каждый ключ из `API_KEYS` ведёт к `OWNER`. Неверный ключ даёт 401.
- Два чата, начатых одинаково, расходятся со второго хода. Перегенерация и правка создают ветку, а не новый чат.
- `merge`: конфликт «живёт в Казани» (старый) против «живёт в Самаре» (новый) — актуален новый, старый в истории. Резервная копия создана.
- Служебные запросы (Open WebUI, LibreChat, эвристика) не пишутся в БД.
- `/v1/embeddings` проксируется с проверкой ключа.

## 13. Реализация (v5.0.0)

Реализовано по §9 (A → U → B → C → D) в ветке `release/v5.0.0`; итоги, тесты по этапам, живой прогон и найденные при регрессе дефекты — [`../audit/v5.0.0-regression.md`](../audit/v5.0.0-regression.md). Отклонения от дизайна:
- холодное извлечение фактов тоже идёт через BackgroundGate и ограничено `EXTRACT_MAX_TOKENS` (живой прогон: без этого малая модель держала единственный слот 300 с);
- recall ищет только по словам вопроса, которых нет в видимой части (окно до вопроса, саммари, дельты), и не повторяет показанные фрагменты;
- резерв головы новой эпохи считается от фактического саммари/профиля (+800/+300 символов), а не от максимумов;
- прогрев передаёт те же поля, что влияют на рендер (`tools`, `tool_choice`, `chat_template_kwargs`, …).
- схема (§5): новые таблицы без повышения `user_version` (создаются `IF NOT EXISTS`, схема остаётся v3). `chat_chain` хранит одну цепочку на чат (`pos`, `msg_hash`, `ts`, без `parent_hash`; правка или перегенерация перезаписывает хвост цепочки того же чата; индекс по `pos = 0`); в `chat_epochs` вместо `prefix_tokens` — `cut_pos`, `elide_pos`, `profile_facts`, `memory`, `date_string`;
- конфигурация (§8): `DELTA_CH` по умолчанию 600; `SET_OLLAMA_NUM_CTX` и чтение `/api/show` не реализованы — для Ollama лимит задаётся `CONTEXT_LIMIT` (и `OLLAMA_CONTEXT_LENGTH` на стороне Ollama), иначе Ollama молча обрежет начало; `CONTEXT_MODE=legacy` — простой сдвиг окна по бюджету без эпох (не код v4.8, `compress()` удалён). Добавлены `EXTRACT_MAX_TOKENS`, `SUMMARY_MAX_CH`, `SUMMARY_INPUT_MAX`, `ELIDE_KEEP_TURNS`, `CHARS_PER_TOKEN`, `PROFILE_CH`.

Актуальный список переменных — таблица «Конфигурация» в [README](../../README.md#конфигурация).
